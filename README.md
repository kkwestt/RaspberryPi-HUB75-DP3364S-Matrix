# DP3364S 128x64 HUB75 panels on Raspberry Pi

Driving P2.5 128x64 HUB75 panels with **DP3364S** S-PWM column drivers from a
Raspberry Pi 4. This uses the experimental S-PWM fork
[angyalr/rpi-rgb-led-matrix_pwm_DP3265S](https://github.com/angyalr/rpi-rgb-led-matrix_pwm_DP3265S)
plus a small patch.

**Status: working.** Geometry, colours and a smooth 12-bit gradient are correct
on one panel and on two chained panels (256x64). The panels recover by
themselves after a power or cable glitch. One known limitation remains: the
brightness flickers while the same Pi runs other memory-heavy work (see
[Limitations](#limitations)).

## Hardware

| Part | Details |
|---|---|
| Panel | P2.5, 128x64, marking `XHFP2.5/3000T0188D`, HUB75 (E on pin 8), 1/32 scan |
| Column drivers | DP3364S (Depuw, S-PWM, 16 ch, 48 pcs per panel) |
| Row drivers | TC7262FJ (Fuman, 138-type, direct A-E addressing) |
| Other ICs | DP245D (input buffer), 74HC04D (inverter) |
| Adapter | iarduino RGB Matrix HAT (74HC245). Pinout = hzeller `regular` mapping, E jumper on pin 8 |
| Host | Raspberry Pi 4 Model B, Debian 13 (trixie), kernel 6.18 |
| Power | 5 V, about 5–6 A per panel at full white |

The stock [hzeller/rpi-rgb-led-matrix](https://github.com/hzeller/rpi-rgb-led-matrix)
leaves this panel completely dark, including with `--led-panel-type=FM6126A`.
DP3364S is an S-PWM driver with on-chip SRAM, and the HUB75 OE pin is its ROW
input.

## What the patch changes

The fork's `dp3265s` profile drives the same Depuw protocol: VSYNC = 3 LAT clocks,
WR_CFG = 5, PRE_ACT = 14, and ROW on the OE pin with W12/W4 pulses. It targets a
64x32 1/8-scan panel, though. All changes are opt-in through environment
variables, and the defaults keep the old DP3265S behaviour.

| Variable | Value here | Why |
|---|---|---|
| `SPWM_DP3265S_REG01` … `REG07` | `REG02=0x021F` | REG02 (LINE_SET) must be 32 lines. The profile hard-codes `0x0207` (8 lines). REG08–REG0D were already overridable; this adds REG01–REG07. |
| `SPWM_DP3265S_SCAN_ROWS` | `32` | The ROW scan loop was hard-coded to 8 rows (`row = (row + 1) & 0x07`, W12 every `64 * 8` rows) in both `SPWM_Display_Scan_Thread::Run()` and `spwm_dp3265s_display_scan()`. With REG02 = 32 lines, each physical row also showed rows ±12/20 lines away. |
| `SPWM_DP3265S_GROUPS` | `64` (default) | PWM groups = REG03 + 1, used for the W12 group-start period. |
| `SPWM_GRAY_BITS` | `12` | Pixel data was MSB-aligned to the full 16-bit word. DP3364S with REG03 = REG04 = 0x3F shows 64 × 64 = 4096 levels (12 bits), so the gradient folded into repeating blocks. Values are now MSB-aligned to N bits. |
| `SPWM_REINIT_MS` | `5000` | Registers were written only once. After a panel power or cable glitch the panel stayed dark until the program restarted. Now the configuration is rewritten periodically. |

Chaining: set `upload_chip_count = 8 × panels` in `/etc/spwm-panel.ini`
(`[dp3265s]` section) and pass `--led-chain=N`. The fork's existing ini handling
uses this value for both data upload and register writes.

`--led-slowdown-gpio=5` was required on the Pi 4. At 2, the image tore into
shifted chunks and black pixels showed noise, which looks like lost DCLK edges.

## Build and run

```sh
git clone https://github.com/angyalr/rpi-rgb-led-matrix_pwm_DP3265S.git rpi-rgb-led-matrix-spwm
cd rpi-rgb-led-matrix-spwm
git checkout 8e4f9805568dabfc71d1b470846786e1a3e9bc89   # commit the patch was made against
git apply ../RaspberryPi-HUB75-DP3364S/patches/0001-dp3364s-128x64-support.patch
make -j4 -C examples-api-use

cd ../RaspberryPi-HUB75-DP3364S/tools
for p in static-test clock; do
  g++ -O2 -I../../rpi-rgb-led-matrix-spwm/include $p.cc -o $p \
      -L../../rpi-rgb-led-matrix-spwm/lib -lrgbmatrix -lrt -lm -lpthread
done

sudo ./run-test.sh ./static-test 1   # one panel: geometry / colour test pattern
sudo ./run-test.sh ./clock 2         # two chained panels: clock with milliseconds
```

- `static-test` draws a 1 px white border and 8x8 corner markers: top-left red,
  top-right green, bottom-left blue, bottom-right white. It also draws three
  horizontal R/G/B gradient bars.
- `clock` shows `HH:MM:SS.mmm` in the largest monospace font that fits, the date,
  a border and thin R/G/B gradient bars. Fonts come from `FONT_DIR`, the
  library's `fonts/` directory.

The same environment variables and flags work with the fork's
`examples-api-use/demo -D0`.

## Measured upload rate (Pi 4, slowdown 5)

| Panels | Canvas | Frames/s |
|---|---|---|
| 1 | 128x64 | ~210 |
| 2 | 256x64 | ~110 |
| 4 | 512x64 | ~57 |

DP3364S keeps the image in its own SRAM, so the upload rate only limits how
fast the content can change.

## Limitations

**Flicker under load.** On DP3364S the grayscale clock (GCLK) is generated by an
on-chip PLL from DCLK (`F_GCLK = F_DCLK × (REG06[2:0] + 1)`). On the Pi, DCLK is
bit-banged, so any memory-bus contention changes the DCLK rate, and the whole
panel's brightness changes with it. `isolcpus=3` does not prevent this, because
all cores share the memory bus. Measured on a Pi 4 that also runs H.264 decoding
and a face-detection network:

| Load on the other 3 cores | Upload rate min / p10 / median, Hz |
|---|---|
| nothing | 189 / 209 / 209 |
| H.264 1080p, hardware decoder | 120 / 204 / 209 |
| H.264 1080p, software decoder | 79 / 191 / 209 |
| hardware decoding + face detection at 3 fps | 45 / 84 / 159 |

With the Pi doing nothing else, the panels are stable and flicker-free. For a
stable image alongside heavy workloads, use a dedicated driver with a hardware
clock, for example an RP2040 with PIO, or a separate Pi for the panels.

## Register reference

DP3364S register values captured from a factory controller on a 1/64-scan panel
(posted by @sonycman in
[hzeller/rpi-rgb-led-matrix#1821](https://github.com/hzeller/rpi-rgb-led-matrix/issues/1821)):

| Reg | 02 | 03 | 04 | 05 | 06 | 07 | 08 | 09 | 0A | 0B | 0C | 0D | 0E | 0F |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| R | 3f | 3f | 1a | 04 | 39 | 00 | 7f | 68 | be | 28 | 58 | 08 | 08 | 20 |

On this panel, applying that full set as is gave washed-out, nearly white
colours, because the REG06 PLL value does not match the fork's timing. Setting
REG0C bits 7:6 = 01 (independent-refresh mode, as the factory controller does)
made no visible difference. Only REG02 is changed.
